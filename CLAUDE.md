## Overview

Indoor football (futsal) management app with three user roles: **PLAYER**, **OWNER** (an indoor field/venue owner), and **ADMIN**. Two independent npm projects live side by side:

- `backend/`: Express 5 REST API (ES modules, `"type": "module"`) + Prisma 6 on PostgreSQL.
- `IndoorFootballApp/`: React Native 0.82 mobile app (plain JS screens; only the template test is TS).

The repository root has no `package.json`: install dependencies and run `npm` inside each subproject. `README.md` (root) is the setup guide for a new PC, and `backend/.env.example` lists every backend variable with fake values; keep both in sync with the code.

**Line endings:** the root `.gitattributes` stores and checks out text files with LF (overriding `core.autocrlf`), keeps `*.bat`/`*.cmd` CRLF, keeps `gradlew` and `*.sh` LF, and marks images, fonts, jars and keystores binary. Prettier 2.x expects LF. The root `.gitignore` ignores `node_modules/`, `.env` and `.env.*` (except `.env.example`), and database dumps (`backup/`, `*.backup`, `*.dump`, `*.bak`, `*.sql.gz`, `*.sql.zip`) in every folder. Plain `*.sql` is deliberately not ignored, so `backend/prisma/migrations/**/migration.sql` stays tracked. Never commit a database dump; `backup/app_db.backup` was untracked on 2026-11-20 but is still in git history until the Phase 0 purge.

## Commands

Backend (run from `backend/`):
```bash
npm install
npx prisma generate          # after any schema.prisma change
npx prisma migrate deploy    # apply migrations; use `npx prisma migrate dev --name <name>` to create one
npm run dev                  # nodemon on src/server.js, port 4000 by default; ignores tests/ (nodemonConfig in package.json); a taken port prints "Port 4000 is already in use…" and exits 1
node scripts/createAdmin.js  # create the ADMIN user, or change its password (reads ADMIN_EMAIL, ADMIN_PASSWORD)
npm test                     # node:test suite in tests/ (needs `npm run dev` running and the local DB)
node --test tests/auth-tokens.test.js   # single test file
```

- **Install scripts (npm 11+):** npm only runs dependency install scripts that are approved in the `allowScripts` field of `backend/package.json`. Approved: `bcrypt` (builds its native code) and the Prisma packages (`prisma`, `@prisma/client`, `@prisma/engines`). While uninstalling packages, npm 11.16 may print a warning that these four aren't covered; `npm approve-scripts --allow-scripts-pending` is the reliable check. Approvals are pinned to exact versions, so after upgrading one of these, or adding a package with an install script, run `npm approve-scripts --allow-scripts-pending` to list what needs a decision. Don't approve anything without asking. The mobile app currently has nothing pending.
- **createAdmin.js** lowercases and trims `ADMIN_EMAIL` (`normalizeEmail`). It refuses to run if `ADMIN_EMAIL` or `ADMIN_PASSWORD` is missing or the password is weak, and never prints the password. It updates an existing admin with that email, and refuses to promote a non-admin account or to create a second admin.
- **Tests:** backend tests use Node's built-in test runner (`node:test`) and `fetch`, with no extra dependencies. They send real HTTP requests to the running local server and use Prisma directly to set up data. Each test creates its own throwaway user (`test-<uuid>@example.com`) and deletes it in `t.after()`. Shared setup lives in `tests/helpers.js`. `tests/config.test.js` and `tests/config-env-file.test.js` are the exceptions: they don't import `helpers.js` and need neither the server nor the database. `config.test.js` tests `loadConfig` directly. `config-env-file.test.js` imports `src/config.js` in child processes: from another folder (it needs the real `backend/.env`, and checks no value is printed), and from a throwaway copy in `tests/.tmp-config-*` with no `.env` next to it (deleted afterwards). Test files run one at a time (`--test-concurrency=1`) because they share the server and database. `authController` never sends mail to `@example.com` addresses (it logs a line instead), so test runs send no real email. Sending to a `.invalid` address fails at once (that domain can never receive mail), which tests use to make sending fail on purpose. Never change existing users in tests. Tokens put straight into the database must be stored as `sha256Hex(token)` (from `tests/helpers.js`), with the plain token sent in the request, like a real email link. Because the server trusts one proxy, `postJson`/`postForm`/`getWithIp` send a random made-up `X-Forwarded-For` address per request, so the suite never trips the rate limits; `tests/rate-limits.test.js` passes a fixed address to hit them. To test that a multi-step delete rolls back, `tests/admin-delete.test.js` passes `deleteUserAndData`/`deleteTeamAndMembers` a wrapped Prisma client that throws at one step inside the real transaction (`failAt`).

Required `backend/.env` variables (see `backend/.env.example`): `DATABASE_URL` (must start with `postgresql://` or `postgres://`), `JWT_SECRET` (at least 32 characters, and not the placeholder from `.env.example`), `EMAIL_USER` (must contain "@"), `EMAIL_PASS` (Gmail SMTP via nodemailer), `BACKEND_PUBLIC_URL` (an `http://` or `https://` URL, used to build the email verify and reset links; a trailing slash is removed), and optionally `PORT` (1–65535, default 4000). Blank or whitespace-only counts as missing. The server checks all of these at startup and refuses to start (exit code 1) with one message listing every bad setting by name and reason, never its value. `ADMIN_EMAIL` and `ADMIN_PASSWORD` are only needed when running `scripts/createAdmin.js`, and `TEST_BASE_URL` only by the tests; none of the three is checked by the server.

**Settings (`src/config.js`, `src/config/loadConfig.js`):** `loadConfig(env)` is a pure function (no dotenv, no `process.exit`) that returns a frozen `{ port, jwtSecret, emailUser, emailPass, backendPublicUrl }` or throws a `ConfigError` whose `problems` list every bad setting. Values are trimmed (spaces at both ends removed) before they're checked and used. `JWT_SECRET` equal to `EXAMPLE_JWT_SECRET` (the `.env.example` placeholder; `tests/config.test.js` checks the two match) is refused. `config.js` loads `backend/.env` from a path based on its own location (`import.meta.url`), so the server finds it whichever folder it's started from; a missing `.env` file is not an error by itself (real hosting supplies settings directly), and settings already in the environment win over the file. It then calls `loadConfig` with `process.env`, and on a `ConfigError` prints the problems and exits with code 1 (no stack trace). `server.js` imports `config.js` first: ES module imports all run before the importing file's body, and `authController.js` builds its nodemailer transporter at import time. (Before this, `.env` was in fact loaded by importing `@prisma/client`, which Prisma 6 does by itself; later Prisma versions don't.) `config.js` is the only file in `src/` that reads `process.env`; everything else imports `config`. `DATABASE_URL` is checked but not in the config object, because Prisma reads it from the environment itself. Never print a setting's value, in errors, logs or tests.

## Architecture

A beginner-friendly explanation of the same system lives in `docs/ARCHITECTURE.md`. This section is the technical reference. Keep both in sync when the architecture changes.

### Backend
`src/server.js` mounts five routers: `/auth`, `/players`, `/owners`, `/teams`, `/admin`. Each route file in `src/routes/` maps to a controller with the same name in `src/controllers/`.
- **Auth middleware** (`src/middleware/auth.js`): login (`authController.login`) signs an HS256 JWT with claims `{ id, userId, role, email, tv }`, valid for 30 days (`LOGIN_TOKEN_LIFETIME_SECONDS` in `src/utils/tokens.js`); `tv` is the account's `tokenVersion`. `verifyToken` (async) requires the header to be exactly `Bearer <token>` (Bearer case-insensitive, one space, no spaces in the token), verifies with `algorithms: ['HS256']`, then looks up the user by `id` and replies 401 "Invalid token" if the user is gone, the token has no integer `tv`, or `tv` isn't the current `tokenVersion` (a missing header is 401 "No token"). `req.user` (`{ id, userId, role, email }`) is built from the database row, never from the token's claims, so role and email changes apply at once. A database error is thrown and reaches the error handler (500), not a 401. `resetPassword` increments `tokenVersion` in the same update as the new password, which logs the account out on every device; password change and suspension must do the same when they're built (Phase 4). `isAdmin` guards every `/admin` route. `playersOnly` (403 for OWNER and ADMIN) guards team create, invite, accept and reject. Other role and ownership checks happen inside the controllers (for example `team.ownerId !== req.user.id`).
- **Errors:** controllers pass failures on with `next(err)` (Express 5 also forwards errors thrown in async handlers). `src/middleware/errorHandler.js`, mounted last in `server.js`, logs the error and replies only `{ "error": "Something went wrong" }` (500) or `{ "error": "Invalid request body" }` (400 for unreadable bodies). Never put `error.message`, stacks or Prisma details in a response.
- **Security middleware** (in `server.js`): `app.set('trust proxy', 1)` because the backend sits behind exactly one proxy (ngrok), so `req.ip` is the visitor's address; don't raise it. `helmet()` with its default content security policy (server-rendered pages must not use inline scripts or styles). Rate limits in `src/middleware/rateLimits.js`, replying 429, tuned for shared mobile IPs (DECISIONS.md 2026-11-19): login counts only failed attempts (`skipSuccessfulRequests`; `requestWasSuccessful` also treats the 403 "please verify" as success, since the password was right), 10/15 min per IP + email and 50/15 min per IP; register 20/hour per IP; forgot and resend-verification each 5/hour per IP + email and 20/hour per IP; reset POST 10/15 min per IP; reset page and verify link GETs 30/15 min per IP each (HTML replies). Keys always go through express-rate-limit's `ipKeyGenerator` (IPv6 grouped by /56); emails are lowercased and trimmed. Counters are in memory and reset on restart.
- **Prisma**: the server has one shared client, `prisma` from `src/db.js`, imported by every controller. Nothing else in `src/` may call `new PrismaClient()` (each client opens its own connection pool). `src/utils/deletion.js` and `visibility.js` take the client as a parameter. `scripts/createAdmin.js` and `tests/helpers.js` are separate programs with one client each. The schema has no `onDelete: Cascade`, so deletes must first remove dependents by hand: `TeamMember` rows, then the user's owned teams and their members, then profiles, then the `User`. All of it goes through `src/utils/deletion.js` (`deleteUserAndData(db, userId)`, `deleteTeamAndMembers(db, teamId)`), which runs every step in one interactive `$transaction` and returns false when the row doesn't exist. Any new multi-step write must also use a transaction. Admin delete routes are `/admin/users/:id` (`deleteUser`: PLAYER and OWNER accounts), `/admin/indoors/:id` (`deleteIndoor`: OWNER accounts only, anything else 404 "Venue not found") and `/admin/teams/:id`. Both account routes share `deleteAccount` in `adminController.js`, which refuses with 403 when the target is the admin's own account or any ADMIN account.
- **Route ordering matters**: in `playerRoutes.js`, `/me` and `/invites` must stay above `/:id`.
- **`GET /auth/me`** (`verifyToken`): the caller's own `{ id, name, email, role, verified }` through `toVisibleUser`; 401 if the token's user no longer exists. Used by the app at start-up.
- **Registration flow**: `POST /auth/register` creates the `User` and its role-specific profile in one nested create, then emails a verification link (valid 24 hours). Login is refused until `verified` is true. `POST /auth/resend-verification` sends a new link to an unverified account (the login screen shows a button for it after the 403). Password reset sends a link (valid 1 hour) to a server-rendered HTML form at `/auth/reset-password-page`, which POSTs to `/auth/reset`. That is why `express.urlencoded` is enabled, with `extended: false` so every form value is plain text (a repeated field becomes an array), never a nested object: `token[not]=x` is a field literally named `token[not]`.
- **Tokens are stored hashed**: the email link carries the random token; `User.verifyToken` and `User.resetToken` hold only `hashToken(token)` (SHA-256 hex). Always store and look up the hash, require the expiry (`verifyTokenExpires` / `resetTokenExpires`) to be in the future, and clear both token and expiry once used. Check `isWellFormedToken` before any lookup of a token from a URL. Reset and resend have a 5-minute per-account cooldown (`sentRecently`), with an unchanged reply.
- **Profile visibility (`src/utils/visibility.js`)**: the one place for "who may see what" (PRODUCT.md, "Profile visibility"). Every endpoint that returns user or profile data must go through it, including new ones. Never hand-filter fields in a controller.
  - `toVisibleUser(user, viewer)`: yourself or ADMIN get everything except secrets; others get only id, role, createdAt, name and the public profile.
  - `toPublicPlayer`: name, position, height and weight only if set; phone only with `canSeePhone`; never email; address hidden until it becomes "Area" in Phase 4.
  - `toPublicVenue`: the business listing is public; the owner's login email only with `canSeeEmail`.
  - `withoutSecrets`: strips password, verify/reset tokens and their expiry times at any depth (used on admin replies).
  - `findAcceptedTeammateIds(prisma, viewerId)`: one query per request; no endpoint returns other players' phones yet.
  - Responses keep their field names; hidden fields are just left out.
- **Registration email failure**: if the verification email fails to send, register still replies 201 with a message pointing to "Resend verification email", and logs the error. A successful password reset also clears any leftover `verifyToken`/`verifyTokenExpires`.
- **Every endpoint that reads a body or query declares a zod schema in `src/validation/`, and its controller reads only `req.valid`.** Reason: unchecked values must never reach Prisma, because objects like `{"not": ""}` get treated as query operators, and wrong types crash Prisma into 500s. Schemas live in one file per router (`authSchemas.js`, `teamSchemas.js`; shared helpers in `common.js`: `charCount` counts code points, `byteCount`, `inStages` runs schemas in order so a request with several problems gets the same first message as before, `requiredText`, `optionalText`). Routes run `validate({ body, query })` from `src/middleware/validate.js` after the rate limiters and auth checks. It puts the parsed, cleaned values on `req.valid.body` / `req.valid.query` (never reassign `req.query`: it's read-only in Express 5) and replies 400 `{ "error": "<first problem's message>" }`. Options: `message` (one fixed reply for any problem; login uses `INVALID_LOGIN`) and `onInvalid(req, res, message)` (a different reply: `/auth/reset` uses `sendResetFailure`, which gives the browser form HTML pages with "Try again" where it helps; the verify and reset-page links use their HTML pages). Unknown fields are stripped, not rejected (the app sends extras such as `profileData.name` for players and a top-level `name` for owners). Messages are short and human because the app shows `error` in an alert; tests and the app rely on the existing ones, so don't reword them. Conventions and limits: DECISIONS.md 2026-11-20 "Input validation conventions and limits". The only `req.body` read outside a schema is `sendResetFailure` peeking at the raw token to build the "Try again" link (only if `isWellFormedToken`), and `rateLimits.js` keys on `normalizeEmail(req.body?.email)`.
- **Ids from URL params are not in the schemas:** every one goes through `parseId` (`src/utils/ids.js`: positive integer within Int range, else null → 400). Never use `Number(...)` or `parseInt(...)` on a URL id. Because validation middleware runs before the controller, a request with both a bad body and a bad URL id gets the body's message.
- **Emails are normalised in one place:** `normalizeEmail` (`src/utils/email.js`) trims and lowercases, and returns null for non-strings or blanks. Register, login, forgot-password, resend-verification, the rate-limit keys, `sendMail`'s example.com check and `createAdmin.js` all use it. Any new place that reads an email must too. Existing stored emails were checked on 2026-11-20: all lowercase, no clashes.
- **Request schemas in `src/validation/`** (see the zod bullet above) and **shared helpers in `src/utils/`:** `email.js` (`normalizeEmail`, see above), `deletion.js` (transactional deletes, see Prisma above), `ids.js` (`parseId`), `password.js` (the one strength rule, used by register, reset and `createAdmin.js`), `visibility.js` (see above), `html.js` (`escapeHtml`: use it for every value inserted into HTML, in emails or server-rendered pages), `tokens.js` (generates verify/reset tokens, checks their format, `hashToken`, link lifetimes and the email cooldown), `emailTemplates.js` (email HTML), `pages.js` (`messagePage` for server-rendered pages, and `isFormRequest`: `/auth/reset` answers HTML to the browser form and JSON to JSON requests). `GET /auth/verify` always answers with HTML pages (it's opened from an email).
- **Login replies** are the same for an unknown email and a wrong password ("Invalid email or password", 400). "Please verify your email" (403) is only returned after the password is correct. An unknown email is still compared against a fixed dummy bcrypt hash, so both cases take about the same time.

### Data model (`prisma/schema.prisma`)
- `User` has an optional `PlayerProfile` (name, phone, position, height/weight) or `OwnerProfile` (indoorName, phone, address, website), chosen by `role`. The display name returned at login comes from `playerProfile.name` or `ownerProfile.indoorName`.
- `User.tokenVersion` (Int, default 0, added by migration `20261120133554_add_token_version`): login tokens carry it, and increasing it cancels all of the account's tokens (logout on every device). Only these events increase it: password reset, password change while logged in, and suspension (DECISIONS.md 2026-11-20, "Which events log out every device"; the last two are Phase 4).
- **"Owner" means two different things.** `Role.OWNER` is an indoor venue owner. `Team.ownerId` is the *player* who created the team, stored as a `TeamMember` with `role: 'captain'` and `status: 'accepted'`. Team "owner-only" actions (invite, remove player, delete team) refer to the team creator, not `Role.OWNER`. `Team.ownerId` will be renamed to `captainId` (planned in `docs/PRODUCT.md`, not done yet).
- `TeamMember.status` is a free-form string. The code only uses `pending` and `accepted`; rejecting an invite deletes the row. Rows are unique on `(teamId, userId)`. **Pending rows are not membership:** `GET /teams` and `/teams/me` return only accepted rows in `members`, and add `pendingInvites` only when the viewer is that team's `ownerId` (shaped by `toTeamResponse` in `teamController.js`; non-captains don't get the field at all). `/players/:id` `totalTeams` and the admin `memberCount` count accepted rows only. Only invites create `pending` rows: `POST /teams/:teamId/join` was removed (it let players accept their own join requests) and gets rebuilt in Phase 4. Accept and reject act only on `pending` rows and return 404 otherwise.
- `POST /teams/create` input is checked by `createTeamSchema` (`src/validation/teamSchemas.js`): name required, text, trimmed, 2–40 characters; description optional, text if given, at most 200 characters after trimming, blank stored as null. Lengths count code points, so Bangla text isn't over-counted. Names needn't be unique. `POST /teams/:teamId/invite` takes `userId` as a positive whole number (`inviteSchema`; the text "5" is refused), at most `MAX_DB_INT` (2147483647, exported from `src/utils/ids.js`, the same limit as `parseId`). Any id from a body that reaches Prisma needs that same limit.
- Registration input is checked by `registerSchema` (`src/validation/authSchemas.js`; the password strength rule itself stays in `src/utils/password.js`). Email: normalised, a valid address, at most 254 characters. Password: the strength rule and at most 72 bytes (bcrypt ignores the rest; counted in UTF-8 bytes). Role PLAYER or OWNER. PLAYER: `name` (top level) 2–50 characters, trimmed; phone exactly 11 digits; position text, trimmed, at most 30 characters (free text until the Phase 4 enum); height 100–250 cm and weight 30–200 kg, numbers or null only; address optional, at most 100 characters, "" stored as null. OWNER: indoorName 2–60 characters, trimmed; phone 11 digits; address required, at most 200 characters; description at most 500 and website at most 200, both optional, "" stored as null. Character limits count code points. "Email already registered" is checked in the controller, after all of these. The register screens repeat the phone, height and weight checks but not the password-strength rule or the new limits. Keep the two sides in sync.

### Mobile app
- `App.js` wraps `AuthProvider` (`src/contexts/AuthContext.js`) around `AppNavigator`. `AppNavigator` switches on `user.role` between `AuthStack`, `PlayerNavigator`, `OwnerNavigator`, and `AdminStack`.
- Player and Owner navigators share a pattern: a bottom-tab navigator (Profile / Settings) nested as the first screen of a native stack, with feature screens pushed onto the stack. Screens are reused across roles (for example `Team/TeamsListScreen` and `Owner/IndoorsListScreen`). Each navigator defines its own route names, so check the right navigator before calling `navigation.navigate`.
- `src/api/api.js` is a shared axios instance that attaches the JWT from AsyncStorage (`src/utils/storage.js`, key `jwt`). Its response interceptor calls the handler registered with `setSessionExpiredHandler` when a request that carried a token gets **401** (never for 403, never for `/auth/login`). `AuthContext` registers it: remove the token, clear `user`, alert "Your session has expired. Please log in again." once (a ref stops repeats; reset on login).
- **App start** (`AuthContext.restoreSession`): with a saved token, `AppNavigator` shows `StartupLoading` while `GET /auth/me` runs (15 s timeout). Success sets `user`; 401 removes the token; anything else sets `serverUnreachable` and shows `ServerUnreachable` with Retry (`retryRestoreSession`), keeping the token, plus a Log out link (`logout()`, which also clears `serverUnreachable`). Both views (`src/screens/Auth/StartupScreen.js`) use only built-in components and no raw colours until the theme module exists. `logout()` always removes the token.
- `TeamDetailScreen` and `MyTeamsScreen` reload from `GET /teams/me` on focus (the `focus` listener also fires on first open); TeamDetail also reloads after a removal (there's no single-team endpoint; it's only opened from My Teams). `AddMemberScreen` filters `/players` using the captain's `/teams/me` entry (members + `pendingInvites`). `TeamsListScreen` shows "+ Create Team" only to `PLAYER`s, and the captain's name from the team's `members` (the captain is always an accepted member). UI text calls the team creator "Captain"; "owner" in the app means a venue owner.

Known bugs and security issues are tracked in `docs/ROADMAP.md`, not here.
